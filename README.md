# ARIA Home

I live in Petoskey, Michigan, where the winters are long and cold. As an electrician, I've worked on houses with major damage from a fault that nobody caught in time. ARIA Home is built to help notice sooner and get the right person moving. It does not repair or control anything.

## What judges should click

1. Start the backend (port 5000) and frontend (port 5173) as in "Try it in 5 minutes" below.
2. Open the page on port 5173. In "Demo controls (synthetic replay)", set "Scenario" to "Trip home, thermostat offline (video)".
3. Click the replay buttons in order: 16:31, 16:52, 18:21, 18:51, 19:51, 20:21, 20:46, 21:01.
4. At 16:52, check the HVAC company card under "Notifications (simulated delivery)" and its "fields sent:" line; click "Acknowledge (simulated)" on the property manager card and confirm the Outcome headline does not change. At 20:46, find the "HVAC completion report" card — it appears only after the 20:21 verification, as corroboration only.

ARIA Home answers one question for a returning homeowner: **Will my property be ready when I arrive, and if something looks wrong, who should respond?**

It is a solo entry in the Meta Global AI Developer Hackathon (Indie Developer track, theme "Build for Your World").

The core idea is simple: an automation starting is not the homeowner's expectation met. ARIA Home connects the evidence — a planned trip, thermostat, room-sensor, electrical and weather records, plus synthetic visual segmentation evidence — coordinates authorized help when something looks wrong, independently detects recovery from later readings, and verifies the result before it reports an outcome.

What works now: a code-computed readiness status explained by a model investigation, deterministic power context with stated limitations, scoped simulated notifications to the homeowner and property manager, follow-up outcomes checked against later measurements, recovery verification stages from `telemetry_missing` to `arrival_met`, and a labeled simulated timeline with replay through arrival. Key endpoints include `GET /api/health`, `GET /api/sources`, `GET /api/provider`, `GET /api/metrics`, `GET /api/power-context`, `GET /api/investigation`, `POST /api/investigations`, `GET /api/follow-ups/<id>`, `GET /api/events`, `GET /api/visual` and `GET /api/visual/image` (synthetic SAM segmentation evidence, recorded by default), and `GET /api/live-power` (optional Emporia read-only panel, off by default).

## How Meta models are used

At runtime the app calls one Meta model, **muse-spark-1.3**, through the Meta Model API, behind a gated live provider. Mock mode is the default and needs no key. A second Meta model, **sam-3.1** segmentation, is available at runtime only behind its own opt-in (`ARIA_HOME_VISUAL_LIVE=1` plus `MODEL_API_KEY`); without it the app replays recorded sam-3.1 responses over synthetic images. The synthetic images themselves are fixtures only, generated by **muse-image-1.0** and never by a runtime call. Every model the app calls at runtime is a Meta model.
The evaluation can also run Muse Spark Open (meta-models/muse-spark-open-1026, a Meta open-weight model) through Baseten's hosted API, evaluation only.

The investigation uses the **inv-v3** contract, which binds the model's claims to the evidence. The model returns structured `facts[]`; each claim type may cite only its allowed evidence fields, values are checked against the evidence pack, and the facts shown as "Verified facts (checked against the evidence)" are rendered by code, not by the model. The model's own wording stays separate under "Interpretation (model-written, not verified)".

The model may explain a computed status, describe supporting and conflicting evidence, and suggest what observation to make at a follow-up. It may not decide:

- **Readiness** — computed in code in `backend/aria_home/readiness.py` (`on_track`, `at_risk`, `cannot_tell`, `arrival_passed`). The prompt states the computed status and any answer that disagrees is rejected. If no valid answer is produced, the app shows a deterministic summary computed by code.
- **Follow-up scheduling** — computed in code; any time the model supplies is checked and replaced if it falls outside the allowed window.
- **Outcomes and recovery verification** — computed in code from later measurements only (`backend/aria_home/outcomes.py`, `backend/aria_home/verification.py`). Human statements and events never set an outcome or advance a verification stage.

The full rules and thresholds are in [Readiness rules](docs/readiness-rules.md).

## Code vs model: who decides what

| Question | Decided by | Why |
|---|---|---|
| Readiness (`on_track`, `at_risk`, `cannot_tell`, `arrival_passed`, incl. target-at-arrival) | Code (`backend/aria_home/readiness.py`, `readiness-policy-v3`) | The status must follow the same thresholds every time; the model is told the computed status and a disagreeing answer is rejected, so agreement is contract-following, not independent accuracy. |
| Follow-up scheduling | Code (`scheduling.py`, `outcomes.py`) | A model-supplied time outside the allowed window is checked and replaced. |
| Outcome and recovery verification (`telemetry_missing` → `arrival_met`) | Code from later measurements only (`outcomes.py`, `verification.py`) | Human statements, acknowledgements, service visits and the HVAC completion report never set an outcome or advance a stage; only later readings do. |
| Explanation, verified facts vs interpretation | Model explains; code renders the verified facts (inv-v3) | Each model fact may cite only its allowed evidence and values are checked against the evidence pack; the model's own wording stays separate and unverified. |
| Is the home warming / is heat useful? | Code, from temperature evidence only | Watts are not heat: circuit activity can show a circuit is drawing power, but only temperature readings can show warming, so electrical-only evidence never yields `on_track` or a warming stage. |

Possible uses (not measured): vacant rentals, seasonal homes, small buildings.

## Results

These are builder-labeled cases on synthetic data — a small sample, not a benchmark of real homes. Full details: [Evaluation](docs/evaluation.md).

**Offline (deterministic, no model):** 17 cases across 9 synthetic scenarios, each run with all sources combined and with only one source kind at a time.

| Condition | Fully correct (of 17) |
|---|---|
| Combined (all sources) | 17 |
| Thermostat only | 12 |
| Room sensor only | 3 |
| Electrical only | 2 |
| Calendar only | 2 |

Combined evidence matches every expected readiness label and every scored verification stage. Single-source conditions mostly fall back to unsupported answers (`cannot_tell`, `telemetry_missing`, `unable_to_verify`) rather than asserting the opposite. Three findings stand out: during the thermostat outage, thermostat-only evidence cannot support even a current-temperature claim, while independent room readings still show no warming; electrical activity alone never supports a useful-heat claim — only temperature evidence can show warming; and the three `visual_*` scenarios add recorded sam-3.1 segmentation over synthetic images — a water detection supporting `at_risk` alongside low indoor temperature, and two zero-object cases (including the recorded frost-pipe false negative) reported as no detection, never as an all-clear — while visual evidence never yields `on_track`, a warming stage, or a verification success.

**Live (operator-run, approved by Brad):** the recorded runs are registered in [Evaluation](docs/evaluation.md) with model ids, provider routes, dates, code snapshots and policy versions — the full run (snapshot 77cafc9, 2026-10-28, inv-v2) was exactly 17 calls, the 17 eval cases on muse-spark-1.3 via the Meta Model API: 11 valid answers with 11/11 readiness agreement, 6 rejected, all six rejections after-arrival cases citing a stale or superseded reading as current; the after-arrival rerun (snapshot efdff57, inv-v3) was exactly 6 calls, only the six after-arrival cases: 5 valid with 5/5 readiness agreement, 1 rejected on a genuine claim-check catch (the answer said "below target" against the resolved target_gap fact). The rerun is not a full re-run, so the two runs are cited separately, never merged into one number. Earlier recorded runs (the pre-Audit-2 run on snapshot 53a06bd, 2026-10-26: 24 calls, 0 rejected; the current-code comparison on snapshot 114be6a, 2026-10-27) are kept in [Evaluation](docs/evaluation.md) and are superseded, not current. Earlier recorded runs (the pre-Audit-2 run on snapshot 53a06bd, 2026-10-26: 24 calls, 0 rejected; the current-code comparison on snapshot 114be6a, 2026-10-27) are kept in [Evaluation](docs/evaluation.md) and are superseded, not current. Readiness agreement is enforced (the model is told the computed status and a mismatch is rejected), so agreement shows the models followed the contract, not that they judged readiness independently. No recorded live run is a current live call, and no cost figure is recorded, so none is stated.

## Try it in 5 minutes

Supported versions: Python 3.12 and Node 22 (CI, `.github/workflows/ci.yml`); developed locally on Python 3.12.7 / Node 25.9.0. Backend runtime pins are in `backend/requirements.lock` (exact versions from `backend/requirements.txt`); dev/test dependencies (pytest) are in `backend/requirements-dev.txt`. Mock mode is the default: no environment variables and no API key are needed, and the investigation is labeled "MOCK - example answer, not live inference".

Terminal 1 — backend, from the repo root:

```
# Windows PowerShell
cd backend
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.lock
pip install -r requirements-dev.txt
```

```
# macOS / Linux shells
cd backend
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.lock
pip install -r requirements-dev.txt
```

```
python -m flask --app aria_home.app:create_app run --port 5000
```

Terminal 2 — frontend, from the repo root:

```
cd frontend
npm ci
npm run dev
```

Open the page it serves on port 5173 (it proxies `/api` to port 5000). Stop each server with Ctrl+C.

**The video scenario:** in "Demo controls (synthetic replay)", set "Scenario" to "Trip home, thermostat offline (video)" — selecting it runs the investigation at 16:31. Then click the replay buttons in order: **16:31, 16:52, 18:21, 18:51, 19:51, 20:21, 20:46, 21:01**. Watch the Outcome headline move from "Thermostat telemetry missing" to "Thermostat reporting restored" (18:21 — reconnection alone closes nothing), "Warming observed" (18:51 and still at 19:51, goal reached but not yet verified), "Temperature goal verified" (20:21), and "Arrival expectation met" (21:01). At 16:52, check the delivered HVAC company card under "Notifications (simulated delivery)" and its "fields sent:" line; click "Acknowledge (simulated)" on the property manager card and confirm the Outcome headline does not change. At 20:46, find the "HVAC completion report" card on the simulated timeline — it appears only after the 20:21 verification, as corroboration only. The full shot list is in [Demo video plan](docs/demo-script.md).

```
npm run build

```

`npm run test:e2e` starts its own backend and frontend servers on ports 5000 and 5173, so stop the dev servers first. It runs the Playwright end-to-end test in the installed Google Chrome (no browser download).

**Recording footage:** `cd frontend && npm run record:demo` drives the real running frontend and backend at 1280x720 in mock mode on a fresh database, and writes one `.webm` clip per storyboard segment to `frontend/recordings/` (ignored by git). It starts the backend with plain `python -m flask ...`, so the backend virtual environment must be active in that terminal (or Flask must be installed for that python): PowerShell `..\backend\.venv\Scripts\Activate.ps1`, macOS/Linux `source ../backend/.venv/bin/activate`.

**Live mode (optional):** set `ARIA_HOME_MODEL_ENABLED=1` to enable live model calls (anything else stays in mock mode), `ARIA_HOME_PROVIDER_URL` to the model API base host, `ARIA_HOME_MODEL_ID` to the model to call, and `MODEL_API_KEY` to the API key (sent as `Authorization: Bearer <key>`). Keys live only in local environment variables; `.env` files are ignored.

**WhatsApp test delivery (optional, off by default):** set `WHATSAPP_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_TEST_RECIPIENT` (the owner's own verified test number, which stands in for the HVAC company) plus `ARIA_HOME_WHATSAPP_LIVE=1`. Only then does the delivered HVAC-company card offer "Send to my test phone (WhatsApp)", an explicit `POST /api/notifications/<notification_id>/whatsapp` that sends the allowed notice once via the WhatsApp Cloud API (`POST https://graph.facebook.com/v25.0/{phone_number_id}/messages`, plain-text message starting "ARIA Home test (synthetic scenario)", rendered from the exact allowlisted payload fields); the card then reads "Sent to the owner's test number on WhatsApp (stands in for the HVAC company)". `GET /api/follow-ups/<investigation_id>` never sends — replay, refresh and repeated GETs make zero HTTP calls. With anything missing, the notice stays exactly as today ("Simulated, no message was sent") and the button is hidden (`GET /api/whatsapp/status` reports only whether live delivery is configured, never any value). Never sent to any other number; at most one real send per notification id ever, so a second POST never re-sends. Field audit: [WhatsApp audit](docs/whatsapp-audit.json), generated from the code.

**Emporia live panel (optional, off by default):** set `EMPORIA_EMAIL`, `EMPORIA_PASSWORD` plus `ARIA_HOME_EMPORIA_LIVE=1`. Only then does `GET /api/live-power` return the owner's real per-circuit watts (read-only via pyemvue, cached 60 s, `source: "live-read-only (owner's home)"`) and the frontend shows a small separate panel, "Your real home, right now (live, read-only, Emporia Vue)". The panel is hidden otherwise, so the judge demo is unchanged. Live watts are display only: never evidence for readiness, warming or verification, never in the evidence pack (watts are not heat).

**Visual evidence (synthetic images, recorded segmentation by default):** the four images under `backend/fixtures/visual/` are synthetic, generated by muse-image-1.0; each `*.sam.txt` is the recorded raw sam-3.1 response for that image and phrase. `GET /api/visual` serves the recorded observation (boxes, counts, caption) and `GET /api/visual/image` serves the image bytes; both are gated by `received_at <= at` like every other record. Live sam-3.1 segmentation is optional and off by default: set `ARIA_HOME_VISUAL_LIVE=1` plus `MODEL_API_KEY` (same Bearer/timeout handling as the existing provider, single POST, no silent retries). Images are never sent anywhere — HVAC payloads may carry only the observation line "visual observation: water detected (synthetic image)". Visual evidence never yields `on_track`, `warming_observed`, `goal_verified` or `arrival_met`, and zero detected objects is reported as no detection, never as an all-clear. Full policy: [Readiness rules](docs/readiness-rules.md).

## Safety and honesty rules

- **Synthetic data only.** Every thermostat, electrical, weather, calendar and contact record is invented for the demo and labeled synthetic, as are the four visual-evidence images (muse-image-1.0 fixtures) and their recorded sam-3.1 responses. No credentials, real travel details or personal contacts appear anywhere. The only real data the app can ever touch is the optional, off-by-default Emporia live-watts panel, which is display only and never stored in the repo.
- **Simulated delivery and control.** Notifications are simulated only by default — every card reads "Simulated, no message was sent", and there is no real email, SMS or push channel. The one exception is the optional WhatsApp test delivery above: only the allowed HVAC-company notice, only to the owner's own test number, at most once per notice. The app reads and explains; it never operates equipment, and scene/command acknowledgements are simulated timeline events that change no physical state.
- **Scoped notifications.** Each audience (homeowner, property manager, HVAC company) has an allowlist of fields it may receive, enforced in code with refusals recorded. The HVAC request carries only property, access, manager contact and relevant observations — never itinerary, email or location — and is sent only after a manager authorization event.
- **Acknowledgement is not resolution.** A simulated acknowledgement is recorded as its own event and never changes readiness, outcome or verification. The same applies to service visits and the HVAC completion report, which is corroboration only and never sets an outcome.
- **No future data in replay.** Records, trip revisions, confirmations, events and notifications are visible only at or after their received/available times, so a replay at any moment shows only what ARIA could have known then.
- **Bounded claims.** Circuit watts never prove useful heat, a fault or equipment power. Verified recovery means recovery of the monitored temperature goal, never a proven repair cause or fault-free equipment. A mock answer is never presented as a fresh live response.

## Known limits

From the day handoffs and the [feature freeze](docs/freeze.md) (initial freeze 2026-10-26 at 4d3bacb, lifted 2026-10-28 for the Audit 3 repair and the integrations that follow; a final freeze date will be set later):

- All data is synthetic and every message, scene, visit and report is simulated; there are no real channels except the optional WhatsApp test delivery to the owner's own test number, and ARIA Home controls no equipment. Email, location, scene, confirmation and service-visit moments have no dedicated UI and appear as labeled simulated timeline cards.
- Room-sensor and blower mappings are synthetic assumptions, not measured physical behaviour. Readiness thresholds are fixed constants, not fitted to a home, and projection is a linear extrapolation that ignores weather, equipment cycling and occupancy.
- The notification allowlists are reviewed by hand, not by an external privacy review; the HVAC request is gated only by a synthetic manager authorization event.
- The evaluation sample is small and builder-labeled: 17 offline cases, one live run per case. The live agreement rate shows the models followed the readiness contract, not independent readiness judgment, and input-token counts are unreliable.
- The committed live results used the pre-Day-7 readiness labels; Day 7 added `arrival_passed` with target-at-arrival, which the live run did not exercise.
- The older follow-up rule and the verification stage can disagree; the UI headlines the verification stage.
- The claim check is bounded — structured facts plus a phrase/number filter — not a semantic verifier of arbitrary prose.
- The Audit 3 repair and the integrations that follow are in scope after the freeze lift on 2026-10-28. Three optional integrations are implemented, all off by default: WhatsApp test delivery of the allowed HVAC notice to the owner's own test number, the read-only Emporia live-watts panel, and live sam-3.1 visual segmentation (recorded responses replayed otherwise). No real email, SMS (other than that test number), location, travel or equipment-control integration is implemented — those stay synthetic/simulated (future directions, no code: [Architecture — future](docs/architecture-future.md)).
